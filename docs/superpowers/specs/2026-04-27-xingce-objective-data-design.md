# 行测客观题库100%闭环设计

## 背景

当前项目的行测客观题库存在几类核心问题：

1. 不同年份、不同卷别的题量不稳定，部分明显不是试卷本身差异，而是提取不完整。
2. 许多文本题选项只有2个或3个，说明提取逻辑和数据审计机制都不够可靠。
3. 模拟考试页面当前只写死了2024年国考三套卷，且页面展示口径没有和题库完整度绑定。
4. 国考之外，省考和事业编也有类似问题，但标准复杂度更高，不能在第一阶段混做。
5. 工作区目前还存在未完成的前端改动，说明需要先建立可验证的规则和稳定的数据流水线，再推进全库修复。

本设计只处理第一阶段：`src/data/xingce/`下的行测客观题数据闭环，不处理申论题库，不处理申论点评逻辑，也不在这一阶段实现解析高亮样式。

## 目标

第一阶段目标是把“国考行测客观题库”做成一个100%可验证、可重复审计、可直接驱动前端展示的标准样板，为后续扩展到省考和事业编提供统一流水线。

完成后的国考行测题库必须满足：

1. 每年每卷总题数与真实试卷一致。
2. 每年每卷五大模块题量分布与真实试卷一致。
3. 同卷题号连续、唯一、无缺号、无重号。
4. 非图片依赖文本题的选项完整，默认应为4个；合法例外必须登记。
5. `year`、`source`、`level`、`category`、`id`、`answer`等关键字段与题目真实归属一致。
6. 模拟考试页只展示审计通过的完整卷，未通过的卷不允许开考。

## 范围

### 本阶段包含

1. 国考行测客观题的数据规则建模。
2. 国考行测统一审计器建设。
3. 国考行测逐年逐卷修复。
4. 前端题库/模拟考试口径与完整度清单对齐。
5. 针对当前断裂前端代码的最小必要修复。

### 本阶段不包含

1. `src/data/shenlun/`下的任何题库修复。
2. 申论题目页面、申论点评、申论解析富文本优化。
3. 解析关键词加粗、高亮、彩色字体等表现层增强。
4. 省考、事业编的批量修复实施。
5. Git历史重写式瘦身。

## 100%验收标准

### 1. 题量100%正确

每套卷都必须有明确的标准题量。对于国考行测，规则必须落实到年份+级别。审计结果中，总题数不得多一题、不得少一题。

### 2. 模块分布100%正确

每套卷的`changshi`、`yanyu`、`shuliang`、`panduan`、`ziliao`题数必须和真实试卷结构一致。错模块视为未完成，即使总题数对上也不能通过。

### 3. 题号100%连续且唯一

同卷必须形成连续题号区间，例如1到135或1到130。任何缺号、重号、跳号都必须算异常。

### 4. 文本题选项100%完整

默认规则：

1. 非图片依赖文本题必须有4个选项。
2. 对错题或其他合法例外只能通过例外规则文件登记。
3. 未登记但出现0/1/2/3选项的题一律算异常。

### 5. 基础字段100%一致

以下字段必须可校验且一致：

1. `year`
2. `source`
3. `level`
4. `category`
5. `id`
6. `answer`

如果题目实际属于2023年副省级言语题，却被写成2024年或判断题，必须视为数据错误。

### 6. 页面展示100%服从清单

模拟考试页和相关筛选页只能使用审计生成的完整度清单驱动展示。页面不允许自行推断“题量差不多就开放”。

## 设计总览

第一阶段将引入“规则表+统一审计器+完整度清单+逐年修复流水线”四层结构：

1. 规则表定义每套卷应该长什么样。
2. 审计器基于规则表扫描全量题库并生成异常清单。
3. 修复脚本按异常清单逐年清零。
4. 完整度清单作为前端唯一可信来源，决定哪些卷可以展示和开考。

## 规则层设计

### `scripts/config/xingce_exam_specs.json`

职责：

1. 定义每套卷的标准总题数。
2. 定义五大模块标准分布。
3. 定义哪些年份存在哪些级别卷。
4. 标识特殊结构，例如2022年起行政执法卷、2025年行政执法资料题数量变化等。

建议结构示意：

```json
{
  "national": {
    "2025": {
      "fushengjia": {
        "total": 135,
        "modules": {
          "changshi": 20,
          "yanyu": 40,
          "shuliang": 15,
          "panduan": 40,
          "ziliao": 20
        }
      }
    }
  }
}
```

### `scripts/config/xingce_option_exceptions.json`

职责：

1. 登记合法非4选项题。
2. 登记图片依赖题或确有结构差异的题。
3. 为审计器提供“豁免但可追踪”的依据。

未登记的0/1/2/3选项题都必须报错，不能静默跳过。

## 审计器设计

### `scripts/audit_xingce.py`

职责：

1. 扫描`src/data/xingce/`下全部行测客观题JSON。
2. 按`source/year/level`聚合。
3. 校验题量、模块分布、题号、字段、选项完整性。
4. 输出结构化异常清单。
5. 生成供前端消费的`src/data/meta/xingce_exam_manifest.json`。

### 审计结果至少要覆盖

1. `missing_questions`
2. `duplicate_questions`
3. `wrong_module`
4. `wrong_level`
5. `wrong_year`
6. `invalid_option_count`
7. `unexpected_total`
8. `unexpected_module_distribution`
9. `missing_required_fields`

### Manifest职责

`src/data/meta/xingce_exam_manifest.json`必须至少包含：

1. 卷标识
2. 来源、年份、级别
3. 标准题量
4. 当前题量
5. 是否完整
6. 异常数量
7. 是否允许模拟考试开考

前端后续只依赖Manifest，不再在组件内部重新统计“看起来是不是够题”。

## 修复流水线设计

### 执行顺序

国考先做，顺序固定为：

1. 2025
2. 2024
3. 2023
4. 2022
5. 2021
6. 2020
7. 2019
8. 2018
9. 2017
10. 2016
11. 2015

每一年内部按级别顺序：

1. `fushengjia`
2. `dishi`
3. `xingzhengzhifa`（如该年存在）

### 每卷内部处理顺序

1. 题量错误
2. 模块错误
3. 题号错误
4. 选项错误
5. 字段错误

### 每轮闭环

每一卷、每一年都必须走完整闭环：

1. 运行审计器。
2. 产出异常清单。
3. 使用共享提取/修复脚本进行修复。
4. 再次运行审计器。
5. 异常全部归零后才允许进入下一卷或下一年。

任何未归零异常都不能带着进入下一阶段。

## 修复能力设计

优先整理为共享能力，而不是继续堆特例脚本。

### 共享能力1：按题号从PDF重提文本题

能力包括：

1. 根据年份、级别、模块、题号定位题目文本。
2. 重新提取选项。
3. 保留页码或上下文证据，便于失败时人工核验。

### 共享能力2：模块归属校正

能力包括：

1. 判断题目在当前文件中是否属于错误模块。
2. 支持在模块文件之间移动题目。
3. 保持`id`、`category`、`level`、`year`同步更新。

### 共享能力3：缺题与重题处理

能力包括：

1. 发现缺号。
2. 发现重复题或错位题。
3. 在证据充分时自动修复。
4. 在证据不足时写入人工核验队列。

### 共享能力4：字段回填

能力包括：

1. `level`标准化。
2. `category`标准化。
3. `id`与题号、年份、卷别同步。

## 人工核验机制

自动修复并不意味着可以默默跳过失败项。对无法自动完成的题，必须生成“人工核验队列”并明确记录：

1. `source`
2. `year`
3. `level`
4. `category`
5. `question_number`
6. 问题类型
7. PDF页码或文本上下文
8. 当前提取结果
9. 期望结果缺口

只有这样，数据修复过程才是透明的，而不是看似修完、实际上偷偷漏题。

## 前端收口设计

### 模拟考试页

`src/app/exam/page.tsx`当前正式版本写死了2024年国考三套卷。第一阶段会改成：

1. 从`src/data/meta/xingce_exam_manifest.json`动态读取完整卷。
2. 只展示`ready=true`的卷，或者明确标记未完成卷不可开考。
3. 不再将多个年份误混为一个固定入口。

### 做题筛选页

`src/app/practice/page.tsx`会统一使用明确的`ExamLevel`类型，并保证筛选条件和题库字段一致，避免混卷或类型漂移。

### 题目详情页

`src/app/practice/[questionId]/page.tsx`与`src/app/practice/[questionId]/QuestionPageClient.tsx`必须恢复到可编译、可导航状态。第一阶段只做结构修复与稳定性收口，不扩展申论或解析表现层功能。

## 验证设计

### 数据级验证

每修完一年必须满足：

1. 审计器输出0异常。
2. 标准题量与模块分布全匹配。
3. 文本题选项完整率达到100%，合法例外全部登记。

### 工程级验证

至少执行：

1. `npx.cmd tsc --noEmit --pretty false`
2. 需要时执行定向脚本验证Manifest与页面读取逻辑

如果类型错误、缺文件、页面断链仍存在，不得宣称第一阶段完成。

### 抽样验证

对每个已修完年份，抽查代表性文件，确认：

1. 题号连续
2. 模块配比正确
3. 字段一致
4. 选项内容完整

## 分阶段实施策略

第一阶段只把“国考行测客观题100%闭环”打穿。

第二阶段复用同一套规则和审计流水线扩展到：

1. 省考行测客观题
2. 事业编行测客观题

第三阶段再考虑：

1. 解析表现层增强
2. 申论题库与申论页面优化
3. `.git`瘦身与大文件治理

## 风险与边界

### 风险1：历史PDF命名复杂

项目中的PDF目录和文件名包含大量中文与特殊结构，自动定位时必须尽量基于规则映射，不能靠手写字符串碰运气。

### 风险2：部分年份题型结构确实变化

不是所有差异都是错误，例如行政执法卷在不同年份的题量结构确有变化。规则表必须显式记录这种差异，避免把真实变化误判为异常。

### 风险3：工作区已有未完成前端改动

当前工作区存在未提交的前端变更，实施时必须严格隔离本阶段提交范围，不能把不相关历史改动一起带进提交。

## 本阶段完成定义

满足以下全部条件时，第一阶段才算完成：

1. 国考行测2015-2025全部卷通过统一审计。
2. `src/data/meta/xingce_exam_manifest.json`生成且可驱动前端。
3. 模拟考试页不再写死2024三套卷。
4. 题库相关页面通过TypeScript编译检查。
5. 所有本阶段提交都严格限定在相关文件范围内，并同步推送远端。

## 后续计划入口

在本设计获批后，下一步应编写实施计划，拆出可执行任务，并按“规则表→审计器→2025修复→2024修复→……”顺序推进。
